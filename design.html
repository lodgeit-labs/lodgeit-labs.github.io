Design for a million calculators

What has to stay true when the constellation is not two dozen calculators on one gateway but millions, run by many operators, paid per call over L402 and found over Nostr.
LodgeiT Labs · November 2026 · design note, draft v1

This page separates what is live from what is planned. Live: the gateway, the contract on Publish, the rounding standard on Rounding, and Nostr-based signing for Proof-of-Control. Planned: L402 payment at calculator endpoints (see why L402, not x402) and a signed registry carried over Nostr relays. The criteria below are written so that what is live today does not need re-architecture when the planned parts arrive.

The one idea: determinism is verifiability

A deterministic calculator returns byte-identical output for the same request, period and rate-table hashes. At scale that property does more than make tests pass: it means any party can check any answer by running the same request against another conformant engine, or against the published source. Trust in a million calculators does not come from trusting a million operators. It comes from every answer being re-computable. Every criterion below protects that.

1. Identity: every answer says exactly what produced it

  • Stable names. Calculator, period and rate table are URNs (urn:sbrm:calculator:{module}:{name}, urn:sbrm:period:{module}:{scope}, urn:sbrm:rate:{module}:{period}:{rate-type}). A name, once published, is never reused for different behaviour.
  • Jurisdiction is explicit. Every registry entry carries a jurisdiction (for example AU) and its statutes, so an agent never infers the country from a module name.
  • The manifest is the fingerprint. Engine version, rate-table hashes and rounding policy travel with every 200. Two answers with the same fingerprint must be identical; two with different fingerprints explain their own difference.
  • Distinct law, distinct name. Two statutory thresholds that happen to share a value today are still two rate tables. Values coincide; provisions do not.

2. Statelessness: the caller carries the state

  • One call computes one period from the facts supplied. Opening balances, prior elections and history come in the request, are taken as given, and are echoed in the working.
  • No accounts, sessions or stored client data in an engine. That is what lets any instance, run by any operator anywhere, answer any call, and what makes horizontal scale a deployment detail.
  • A multi-year result is a chain of single-year calls, each reproducible on its own.

3. Canonical requests and receipts

  • Canonical form. A request has one canonical serialisation (JSON Canonicalization Scheme, RFC 8785), so its hash is the same wherever it is computed.
  • Receipt key. sha256(canonical request ‖ calculator URN ‖ period URN ‖ engine version ‖ rate-table hashes ‖ rounding policy) identifies an answer. Identical keys mean identical answers, which makes answers safely cacheable and retries idempotent.
  • Signed receipts (planned). An operator may sign the receipt key and response hash with its Nostr key, giving the caller a portable, offline-verifiable record of who computed what.

4. Numbers

  • Decimal strings on every wire, including hops between an operator's own services. No binary floats anywhere on the path.
  • One rounding standard, named in every response, changed only by a new dated policy (Rounding).
  • Money in is cent-quantised or refused. Statutory day counts follow the statute.

5. Rate tables are published, hashed facts

  • Every year-dependent value (a car limit, a threshold, a benchmark rate) is a rate-table node with a primary-source citation and a content hash, served at /v1/rates/{period_uri}. None is a constant in code.
  • There is one source per value. An engine that holds its own copy tests it against the published table, so the two cannot drift.
  • New income years are added ahead of time, on a calendar, not when a caller first hits a refusal.

6. Refusals are a shared vocabulary

  • The status codes are contractual: 422 malformed, 400 refused with a refusal_class, 404 unknown name or period, 5xx operator fault.
  • Refusal classes come from a published list, so an agent can act on a refusal from a calculator it has never seen (for example: ask for a missing effective life, or try another period).
  • A calculator that cannot answer refuses. It never guesses, and never fills a gap with a model.

7. Payment: L402 at the edge planned

  • Price in discovery. Each calculator states its price per call, so an agent knows the cost before it calls.
  • Validate before invoicing. A malformed, unknown or refused request (422, 404, 400) is answered without payment; an invoice is issued only for a request the engine can compute.
  • Payment is the credential. The macaroon is scoped by caveats to the calculator URN, period and an expiry, and the paid preimage proves settlement. No account, no key, no signup.
  • Retries are free. A retry carrying the same proof and the same receipt key gets the same answer without a second charge.
  • Operators are paid directly. Payment goes to the operator's endpoint; LodgeiT charges a routing fee only on calls that come through its own gateway or MCP surface.

8. Discovery and trust over Nostr planned

  • Registry entries are signed events. An operator publishes each calculator as a signed, replaceable Nostr event: URN, base URL, jurisdiction, input schema reference, price and current manifest fingerprint. Relays are interchangeable carriers; the signature, not the relay, is the source of truth.
  • Attestations are signed events too. A conformance result is signed by whoever ran it; a practitioner attestation is signed by the practitioner. The tiers on Publish (unattested → conformance-passed → practitioner-attested → jurisdiction-owned) become verifiable claims an agent checks before it calls.
  • No LodgeiT endpoint in the trust path. As with Proof-of-Control, verification is a signature check against public keys over public relays.
  • Existing building blocks first. Event kinds will use established NIPs where they fit (addressable events for registry entries, labels for attestations, and the data-vending-machine pattern for paid jobs) before anything bespoke is defined.

9. Operating a fleet

  • Reproducible builds. Dependencies are pinned and locked; the deployed image is identified by digest. A library upgrade that changes output is a change, not an accident.
  • Canary deploys. A new version serves no traffic until a smoke test against it passes.
  • One conformance suite, run by anyone. The same suite LodgeiT runs at listing is published, so an operator can run it before asking and a caller can run it at any time.
  • Independent re-runs. Disagreement between independent implementations is the cheapest way to find a defect; the constellation invites it.
  • Engines behind a gateway stay private. Where an engine sits behind a gateway, only the gateway can call it; the public surface is the gateway's.

What we will not do

  • Put a model in a calculation path.
  • Change rounding, rates or behaviour under an existing name or policy.
  • Plug a residual to make a schedule close or a total foot.
  • Require an account, a key or a client library to get an answer.
  • Ask callers to trust an operator instead of checking the answer.

Comments and objections are welcome; the design is meant to be argued with before it is built. — Andrew Noble, LodgeiT Labs
